# LAOS v0.8 Design

## Objective

Implement a minimal, executable Local Agent Operating System on top of the
existing Research Agent Memory v0.7 code. LAOS v0.8 must make every exposed
capability an Agent, keep the Orchestrator free of business logic, make the
Review Agent and Review Gate the only public path that can promote a candidate
to active memory, and build minimal deterministic context that never exposes
restricted or non-active memory.

The implementation preserves all existing v0.7 command-line and Python import
contracts. Markdown and JSONL remain authoritative. SQLite remains a deletable,
rebuildable local index outside synchronized data roots.

## Scope

The implementation adds only the modules named in the LAOS v0.8 objective,
the package initializers required to import them, one focused LAOS test module,
concise README usage, and the narrow compatibility edits required to route the
existing review CLI through Review Agent. It does not add a GUI, service,
database, vector store, model dependency, plugin framework, autonomous
approval, or background process.

## File Map

The implementation creates every required objective path:

- `src/laos.py`: JSON CLI and application composition root.
- `src/orchestrator.py`: public routing-kernel compatibility entry.
- `src/orchestrator/orchestrator.py`: single routing-only implementation.
- `src/agents/base.py`: strict Base Agent contract and envelope validation.
- `src/agents/registry.py`: registry loader and exact task-type selection.
- `src/agents/registry.yaml`: declarations for `import_agent`,
  `memory_agent`, `search_agent`, `review_agent`, and `context_agent`.
- `src/agents/orchestrator.py`: the five concrete Agent adapters.
- `src/memory/core.py`: read and candidate-oriented Memory Core facade.
- `src/memory/store.py`: validated Markdown store adapter.
- `src/memory/candidate.py`: candidate-only creation path.
- `src/memory/lifecycle.py`: states and transition validation.
- `src/review/gate.py`: four-action Review Gate and active-write authority.
- `src/context.py`: public context-builder compatibility entry.
- `src/context/builder.py`: single bounded active-only implementation.

The top-level compatibility entries contain imports only; they do not duplicate
logic. The implementation also creates only the `__init__.py` files needed to
import these packages, updates `src/memory_distill.py` only where its public
review entry points must route through Review Agent, adds `tests/test_laos.py`,
and adds concise `README.md` usage.

## Compatibility Strategy

The required `src/memory/` package conflicts with the existing
`src/memory.py` module because Python prefers a regular package over a module
with the same import name. `src/memory/__init__.py` will therefore act as a
compatibility facade: it loads the existing `memory.py` implementation under a
private module name and re-exports its public and compatibility-required
symbols. Executing `python3 src/memory.py ...` continues to use the existing
file unchanged, while `import memory` and `import memory.core` resolve through
the facade.

The facade is infrastructure, not a capability. It contains no task or memory
business decisions.

Legacy status `conflict` remains readable for v0.7 compatibility. New LAOS
outputs use the objective's canonical status `conflicted`. The store adapter
normalizes legacy `conflict` to `conflicted` when data crosses the LAOS API
boundary; it does not rewrite existing memory merely to change spelling.

## Task Contract

LAOS accepts one JSON object with this common shape:

```json
{
  "type": "memory.search",
  "input": {},
  "trace_id": "optional UUID",
  "context_limit": 8000
}
```

`type` is required and must be registered. `input` defaults to an empty object
and must be an object. `trace_id`, when supplied, must be a UUID. When omitted,
the Base Agent derives a deterministic UUID5 from the canonical JSON task.
`context_limit` is a positive integer and defaults to 8,000 conservative
tokens.

Supported task types are deliberately limited to the five required agents:

- Import Agent: `import.file`, `import.chatgpt`
- Memory Agent: `memory.create`
- Search Agent: `memory.search`
- Review Agent: `memory.review`
- Context Agent: `context.build`

The CLI accepts `--root`, optional `--state-dir`, and exactly one of
`--task-json` or `--task-file`. It writes one JSON object to stdout. Expected
input, routing, validation, and storage failures write a safe JSON error to
stderr and return non-zero.

## Agent Contract and Output

`BaseAgent` defines exactly the required interface:

```python
class BaseAgent:
    agent_id: str
    handles: list[str]

    def can_handle(self, task) -> bool: ...
    def run(self, task, context) -> dict: ...
```

Every successful Agent call returns exactly these top-level fields:

```json
{
  "agent_id": "search_agent",
  "task_type": "memory.search",
  "output": {},
  "candidates": [],
  "requires_review": true,
  "metadata": {
    "trace_id": "UUID",
    "confidence": 1.0
  }
}
```

The required value of `requires_review` is always `true`, including read-only
Agents. Read-only outputs have an empty `candidates` list. Candidate creation
returns candidate identifiers in `candidates`; it never returns an active
record.

## Registry

`src/agents/registry.yaml` uses JSON syntax, which is valid YAML, so it can be
loaded with the Python standard library. Each entry has only `id`, `class`, and
`handles`. `AgentRegistry` validates duplicate IDs, duplicate task handles,
unknown class names, and malformed configuration before instantiating Agents.

Routing is an exact match on `task.type`; there is no heuristic classifier and
therefore no hidden business logic in the Orchestrator.

## Components

### Core Orchestrator

`src/orchestrator/orchestrator.py` performs only the mandated sequence:

1. Validate and classify the task by reading `task.type`.
2. Ask the registered Context Agent for bounded context, unless the requested
   task itself is `context.build`.
3. Ask the Registry for the Agent that handles the task type.
4. Call that Agent with the unchanged task and prepared context.
5. Validate the returned Agent envelope.
6. Return that envelope unchanged.

The Orchestrator receives its Registry as a constructor dependency. It does
not import memory, review, context, or import implementations and has no file
write primitive.

### Agent Implementations

`src/agents/orchestrator.py` contains the five small concrete Agent adapters
required by the objective. Each business capability lives inside the relevant
Agent's `run()` method and delegates storage primitives to the infrastructure
modules:

- Import Agent calls the existing safe manual or ChatGPT import implementation.
  Imports archive raw evidence but do not create active memory.
- Memory Agent validates a create request and calls Candidate Store. It may
  create only `candidate` records.
- Search Agent invokes the canonical existing search implementation with
  `include_restricted=False` and `include_inactive=False`; callers cannot
  override those values through LAOS.
- Review Agent validates the four allowed review actions and is the only Agent
  that receives the Review Gate capability.
- Context Agent calls Context Builder and never accesses unrestricted export or
  inactive-search switches.

### Memory System

`src/memory/lifecycle.py` defines canonical states:

```text
raw, candidate, active, deprecated, conflicted, archived
```

Review is an operation, not a persisted state. Allowed persisted transitions
are:

```text
raw -> candidate
candidate -> active | archived | conflicted
active -> deprecated | conflicted | archived
```

Only Review Gate may request a transition whose target is `active`.

`src/memory/store.py` adapts the existing validated Markdown store. Public
methods are read-only. Mutation primitives are private and require the Review
Gate authority object for any transition to `active`.

`src/memory/candidate.py` creates candidate records through the existing
distillation implementation. It rejects any caller-supplied active status.

`src/memory/core.py` composes lifecycle validation, Store, and Candidate Store.
It exposes reads and candidate creation. It does not expose an activate method.

### Review Gate

`src/review/gate.py` accepts only:

- `accept`: promote an eligible candidate to active.
- `reject`: archive the candidate with a reason.
- `merge`: merge only the existing safe list fields and archive the candidate.
- `conflict`: preserve both records and mark the candidate conflicted.

Any other action fails before a file write. Review Agent owns the sole Gate
instance made available by the application composition root. Candidate and
active records are revalidated before replacement. Existing atomic replacement,
index refresh, verification, and rollback behavior is reused.

The legacy `memory_distill.py accept` and `reject` commands remain available,
but their public handlers construct a Review Agent and submit the equivalent
review task. Review Agent then calls Review Gate. The existing low-level apply
implementation becomes private infrastructure that requires Gate authority, so
Review Agent is the only capability and Review Gate is the only infrastructure
gateway that can promote active memory.

### Context Builder

`src/context/builder.py` requests canonical search results with inactive and
restricted inclusion permanently disabled. It accepts only active memory rows,
normalizes text, removes duplicates, ranks by canonical search score followed
by stable ID, and appends entries until the limit is exhausted.

Without adding a tokenizer dependency, the builder uses a conservative budget:
each Unicode code point counts as one token. This can underfill an LLM context
for ASCII text but cannot exceed the configured count under the builder's
defined contract. It never falls back to a full-memory dump when search returns
too little data.

The pack contains the task type, bounded entries, source identifiers, budget,
and used count. It contains no current timestamp. The same task and store state
therefore produce byte-for-byte equivalent JSON after canonical serialization.

## End-to-End Flow

Candidate creation and review are intentionally separate invocations:

```text
memory.create task
  -> Orchestrator
  -> Context Agent
  -> Memory Agent
  -> Candidate Store
  -> candidate Agent envelope

memory.review task with candidate_id and explicit action
  -> Orchestrator
  -> Context Agent
  -> Review Agent
  -> Review Gate
  -> Memory Store
  -> active, archived, or conflicted result
```

No pipeline stage automatically submits the second task.

## Error Handling

Modules raise one small LAOS exception carrying a stable code and safe message.
The CLI maps known failures to a non-zero exit and a single JSON error object.
Unexpected exceptions are not converted into a success result. Sensitive
record content, restricted excerpts, stack traces, and raw imported content are
not included in error output.

Agent result validation rejects an incorrect agent ID, task type, candidate
shape, `requires_review` value, confidence type/range, or non-UUID trace ID.

## Testing Strategy

Implementation follows the objective's six mandatory steps and test-first
development. One new `tests/test_laos.py` module covers:

1. Base Agent contract, deterministic envelope, and Registry validation.
2. Correct routing, context retrieval order, unchanged result collection, and
   proof that Orchestrator has no memory dependency or write effect.
3. Import, search, and candidate adapters; candidate creation cannot yield
   active memory.
4. Rejection of unknown review actions and proof that only Review Agent plus
   Gate can activate a candidate.
5. Active-only context, relevance, stable ordering, strict budget, and zero
   restricted leakage.
6. CLI end-to-end create, explicit review, active retrieval, safe JSON errors,
   and non-zero failure exits.

After every modification, the focused LAOS tests and all existing tests run.
Final verification also runs `compileall`, checks every required path exists,
searches for prohibited direct active-state mutation outside Review Gate, and
executes a temporary-root CLI smoke test. No real memories or persistent
database files enter the worktree.

## Acceptance Evidence

Completion requires all of the following evidence:

- Every required source path exists and imports on Python 3.11 or later.
- Registry lists all five required Agents and no capability bypasses it in the
  LAOS CLI.
- Orchestrator tests prove routing-only behavior and zero writes.
- Candidate tests prove candidate creation and failed bypass attempts.
- Review tests prove four-action validation and exclusive activation.
- Context tests prove active-only, relevant, deterministic bounded output and
  zero restricted leakage.
- The complete pre-existing suite remains green.
- CLI smoke tests demonstrate the explicit candidate-to-review-to-memory flow.
- Git status contains only scoped source, test, documentation, and registry
  changes; no memory data, PDF, database, cache, secret, or internal material.
